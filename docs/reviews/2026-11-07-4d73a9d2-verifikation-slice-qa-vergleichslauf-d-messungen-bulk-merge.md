## Ursachen-Behauptung des Fix (`PaketweiseSchreiben`)

Die Behauptung lautet: trägt ein TLS-Record zum Server mehrere Pakete einer Nachricht 7 oder den Teil eines Pakets, beendet der Server die Verbindung ohne Antwort; der Mechanismus im Server ist nicht festgestellt.

* **Belegt, mit eigenen Läufen:** Zusammenhang mit dem Schnitt der Records. Mit der Mutation (Weitergabe je Lesevorgang) 18 von 20 rot (Reset durch die Gegenseite, Enden der Pumpe „Server->Client beim Lesen: Connection reset by peer“); mit dem Fix 64 von 64 grün, je Instanz 32. Der Unterschied ist bei jeder vernünftigen Annahme über die Grundrate kein Zufall.
* **Ehrlich begrenzt:** Das Protokoll schreibt „Grund“, ergänzt aber „Nicht festgestellt: warum der Server so reagiert … belegt ist der Zusammenhang mit der Aufteilung der Records, nicht der Mechanismus im Server“. Das trägt. Ein Reset einer Seite beweist nicht, dass der Server der Auslöser ist (ein Fehler des Proxys beim Zusammenfassen ist eine zweite Lesart; gegen sie spricht, dass `MESSUNG_DIREKT=1` ohne Proxy 0 von 40 rot ist und der Fix am Record-Schnitt ansetzt). Die Aussage „Server beendet“ bleibt Lesart, die Messaussage ist der Zusammenhang; so steht es.
* **Nicht belegt, aber gesagt:** Der Satz im Protokoll „schreibt jedes TDS-Paket … zum Server“ nennt nur eine Richtung; der Code ruft `PaketweiseSchreiben` in beiden Richtungen auf (V-7). Ein unvollständiges Paket am Ende des Stroms geht verloren (`rest` wird nicht geschrieben).
* **Wirkung auf andere Läufe:** `LAUF=mitschnitt` nutzt `TlsAufnahme` nicht: Exit 0, Ablage unverändert. `LAUF=wire`: Exit 0; die Ablage ändert sich nur in PRELOGIN, Datum und der Anmeldeantwort des Servers (Inhalt des Servers). Die Mutation wird von 2 Unit-Tests erkannt (rot), nicht vom Rest der Suite. Keine Regression gegen die bisherigen Ablagen.
