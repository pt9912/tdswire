# Ein Akzeptanzkriterium nennt den Standardpfad eines fremden Werkzeugs, und der Treiber scheitert dort vor dem Server

**Sub-Area:** `*` (Lastenheft, Prüfclient)

[TDS-FA-12](../../../../../../spec/lastenheft.md#tds-fa-12--testserver-mit-veränderlichem-arbeitsspeicher-bestand-und-prüfclient-d-migrate) verlangt `data import` und `data transfer` „im Standardpfad des Werkzeugs“. Der Spike ([Messprotokoll](../../../../../messungen/callback-loesung-spike-2026-11-05.md) b3) fand: mssql-jdbc 13.4.0 scheitert im Massenladen an INT-Spalten und an ganzzahlig geschriebenen DECIMAL-Werten, bevor der Server Zeilen sieht; `--on-conflict skip` umgeht es nur mit Verengung Int64 auf Int32, angepasstem Parser und unterhalb der Handle-Grenze. Das Kriterium ist für Tabellen mit INT-Spalte nicht erfüllbar, ohne den Treiber zu ändern; die Gegenmessung an einem echten SQL Server steht aus (EULA-Entscheidung des Nutzers). **Benannte Spec-Lücke:** das Lastenheft führt keinen Vorbehalt für Spalten, die der Treiber selbst ablehnt. Der Nutzer hat für die Beispieltabellen BIGINT-Schlüssel gewählt ([ADR-0033](../../../../adr/0033-callback-loesung-fuer-schreiben-struktur-und-massenladen.md), Entscheid 7); den Wortlaut des Lastenhefts ändert der Planner nicht.
